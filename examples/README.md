# Example datasets

Thirteen small datasets, each built by [`build.py`](build.py) from a fixed seed. Twelve of
them plant exactly one fault so a finding can be traced to one cause; the two named
`leaky_*` fixtures combine them the way a real project does.

[`RESULTS.md`](RESULTS.md) is the audit output for these bytes. It is generated by a run,
never written by hand, so the verdicts quoted below are what the tool said on the machine
this was built on - not what the fixtures were designed to trigger.

```bash
python examples/build.py            # (re)create every fixture next to this file
python examples/build.py --audit    # ...and regenerate RESULTS.md from a live run
dataset-doctor-audit audit examples/unsafe_group_leakage
```

## The measured point of the collection

| fixture | planted | verdict | what lit up |
| --- | --- | --- | --- |
| `safe_tabular` | nothing | `FORMAL_EVAL_SAFE` | 2 LOW, 1 INFO - no critical or high finding |
| `unsafe_duplicate` | 5 verbatim train rows inside test | `FORMAL_EVAL_INVALID` | DD003 CRITICAL |
| `unsafe_group_leakage` | 4 patients re-booked under new record ids | `FORMAL_EVAL_INVALID` | DD005 CRITICAL, no DD003 |
| `unsafe_label_conflict` | identical features, flipped label | `FORMAL_EVAL_INVALID` | DD009 CRITICAL, plus DD005 on the same rows |
| `unsafe_target_leakage` | a column derived from the label | `FORMAL_EVAL_INVALID` | DD007 CRITICAL + DD007 MEDIUM candidate |
| `shifted_tabular` | covariate and label shift, no leakage | `FORMAL_EVAL_RISKY` | DD012/DD013 HIGH - and no leakage rule |
| `leaky_patient_dataset` | entity + duplicate + target leakage, future-dated train | `FORMAL_EVAL_INVALID` | DD005 x3, DD006, DD007 x3 |
| `safe_image` | nothing | `FORMAL_EVAL_SAFE` | 1 LOW, 1 INFO |
| `unsafe_image_duplicate` | 4 byte-identical images inside test | `FORMAL_EVAL_INVALID` | DD003 CRITICAL |
| `unsafe_near_duplicate` | 3 brightness-shifted pairs across the boundary | `FORMAL_EVAL_RISKY` | DD004 HIGH |
| `unsafe_image_label_conflict` | one image under three class folders | `FORMAL_EVAL_INVALID` | DD009 CRITICAL, plus DD003 for the copy inside test |
| `corrupt_image` | a truncated JPEG and a zero-byte PNG | `FORMAL_EVAL_RISKY` | DD016 HIGH, 2 of 36 |
| `leaky_image_dataset` | 10 exact + 6 near duplicates, 3-way conflict, 2 corrupt, imbalance | `FORMAL_EVAL_INVALID` | DD003, DD004, DD009, DD016 |

`shifted_tabular` is the row that justifies the project. Its test split is an older,
heavier, mostly male population with a 75% positive rate - a genuine problem, and
deliberately *not* leakage. The tool reports it as HIGH shift and `FORMAL_EVAL_RISKY`,
never as a blocked evaluation, because a data quality issue and an evaluation validity
issue call for different fixes. Conflating them is how audit tools get ignored.

`unsafe_group_leakage` is the row that justifies the tool. Nothing in it is a duplicate:
every row is unique by content and by id, so a dedup pass finds nothing. The only way to
see it is that `patient_id` `p000`-`p003` appear on both sides of the boundary.

## Reading one

```
examples/unsafe_group_leakage/
├── PLANTED_FAULTS.md     # what was planted, and where
├── dataset-doctor.yaml   # the same config a user would write
├── train.csv
└── test.csv
```

Each `PLANTED_FAULTS.md` also names the findings that arrive *with* the planted one. An
exact row duplicate always carries its entity across the boundary, so DD003 and DD005 fire
together - that is one fault seen from two sides, and the note says so rather than
pretending the fixture is tidier than it is.

## Ground rules

- Data is generated, never committed by hand: same seed, same bytes, same verdicts.
- Nothing here is real patient or image data, and no fixture is used to claim accuracy on
  a public benchmark.
- The image fixtures total 51-100 files each, so the whole collection audits in seconds.
